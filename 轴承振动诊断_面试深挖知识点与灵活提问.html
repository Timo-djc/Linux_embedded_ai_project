01项目介绍与五层框架

项目面向旋转设备的轴承状态诊断。分类目标有四类：正常、滚动体故障、保持架故障、外圈故障。系统在树莓派端完成采集、图像化特征处理、推理与现场输出。

AD4134 或 CSV→三轴样本块→CWT 与 CCWF→ONNX 四分类→告警、显示与日志
90 秒项目介绍

系统每次将 X、Y、Z 三轴信号按轴打包。处理线程对每轴做连续小波变换，把时频幅度转换为灰度图，再按局部相关性融合。融合图以 1×1×224×224 的浮点张量输入 ONNX Runtime，模型给出四类分数。业务层按置信度阈值与告警延迟规则决定是否驱动继电器等现场输出，同时更新 OLED 和日志。采集与日志使用队列和处理线程解耦，CSV 回放用于复现预处理与推理问题。

S为什么拆成五个框架？分别承担什么？

答。采集框架统一真实 ADC 与模拟输入，处理框架生成融合图，AI 框架负责张量和会话，显示日志框架持久化与查询，扩展框架负责菜单和现场接口。BearingVibrationProject 持有模块、启动工作线程并做告警决策。框架描述的是职责，工作线程描述的是调度，两者可独立调整。

变式。“换传感器或模型会影响哪里？”传感器可集中改采集层，但量程、安装方向和采样率改变会传导到模型分布。换模型先核对张量形状、归一化、类序和分数语义。

S这是故障诊断、故障预测，还是振动标准评估？

答。当前主链实现窗口级故障分类与规则告警。维护计划、历史分析等接口不能据此声称完成 RUL 预测。预测剩余寿命需要带退化过程或失效时间的长期数据。做标准评估还需要明确量纲、频带、测点、机器类别及适用规范。当前网络输入是归一化的图像。

02AD4134 与采样时序

代码路径。SPI 用于寄存器写入与回读校验。数据读取等 ODR 低后再等其变高，然后用 GPIO 翻转 DCLK，在每个时钟周期读取 DOUT0、DOUT1、DOUT2 各一位。24 次循环后分别符号扩展，按 raw × 4.096 / 2²³ 得到代码使用的电压值。每批 5000 帧，每帧三通道，落入连续的 [X₀…X₄₉₉₉ | Y₀…Y₄₉₉₉ | Z₀…Z₄₉₉₉]。

S为什么有 SPI，又有 ODR、DCLK 和 DOUT？

答。SPI 是配置通路，ODR/DCLK/DOUT 是当前代码的采样数据通路。ODR 的边沿用于同步帧，DCLK 推进位读出，三根 DOUT 并行承载三个轴。三轴并行读一帧要 24 个 DCLK 周期。需要对照芯片数据接口模式及实测波形确认有效采样边沿和时序裕量。

S24 位的 0xFFFFFF 等于多少？50 k 帧/秒时位时钟下限是多少？

答。0xFFFFFF 符号扩展成 0xFFFFFFFF，值为 −1。0x800000 为 −2²³。代码对应约 0.488 µV/码的换算步长，这个步长不代表系统噪声或实际有效位数。按三路并行、每帧 24 位计算，理想平均位时钟下限为 1.2 MHz，还要留帧间和 GPIO 操作开销。三路合计原始位流为 3.6 Mbit/s。

S你怎么证明在 Linux 用户态没有丢样？拔掉 ADC 后还能退出吗？

答。50 kHz 是代码标称值，set_sample_rate() 在设备层也未实际调硬件。用逻辑分析仪同时看 ODR、DCLK 与 DOUT，核对 ODR 周期、每帧 24 个脉冲及帧漏读，在 CPU 和 I/O 负载下复测。当前 ODR 忙等没有超时或停止检查，信号卡住时采集线程可能卡在读帧，进而阻塞 join()。

拓展。先加超时、停止检查和故障状态。若实测无法在每个窗口跟上时序，再评估硬件采集外设或 MCU/FPGA 聚合并带序号传输，分别验证有效采样率、漏帧与停止时延。

A24 bit 就有 24 bit 有效精度吗？如何换算为 g？

答。标称位宽只给数字码的粒度。有效精度受噪声、参考源、增益、带宽和传感器限制。要从电压求加速度，需要传感器灵敏度和偏置，并考虑模拟前端的增益。当前源码追到的是 ADC 码转电压，拿已知激励做标定才能得到可溯源的 g 值。

03窗口、频率与故障机理

按标称 fs = 50,000 Hz，N = 5,000
观测窗 N/fs = 100 ms     奈奎斯特频率 fs/2 = 25 kHz
若对完整窗口做 N 点 DFT，频率栅格 fs/N = 10 Hz
每块三轴 float 原始载荷 = 3 × 5000 × 4 B = 60,000 B（约 58.6 KiB）
S采样率 50 kHz，为什么界面没有每秒输出 5 万次？

答。采样率是每轴采样点/秒。模型按 5000 帧一块输出，采集线程每个成功块后还休眠 500 ms。假设硬件连续以标称速率读完一个块需要约 100 ms，块起点间隔粗略约 600 ms 加其他开销。模拟回放无需等真实采样，节奏主要受休眠与开销影响。100 ms 是信号观测窗，输出节奏还受队列、预处理和推理影响。

变式。“能说无间隙监测吗？”按当前批次休眠的实现，应测相邻块间未覆盖时间，并评估短暂事件是否在间隙丢失。

A外圈、滚动体、保持架故障为什么在振动里可区分？

答。缺陷经过受力接触区可产生重复冲击并激发结构共振，重复频率随转速和轴承几何变化。理论上可用 BPFO、BSF、FTF 分别讨论外圈、滚动体自转、保持架的特征频率，再结合包络谱与谐波检验。当前分类入口用时频图。特征频率是解释和复核的工具。

变式。“换转速后能识别吗？”固定像素里的频率纹理可能迁移。用留出转速验证，若可读到转速，考虑阶次分析或按转角重采样，比较跨工况召回率。

A把 100 ms 窗口补零到 1 秒，是否就能分开相差 1 Hz 的成分？

答。补零让频谱采样栅格更密。实际可分辨性主要受观测时长、窗形与信噪比约束。真要分开很近的频率，要增加有效观测时间或使用有明确假设的估计法。这里的 10 Hz 是 DFT 栅格，CWT 的分辨率由小波和尺度决定。

04CWT 与 FFTW 实现

为什么要做时频图。全窗 FFT 给出窗口整体频谱。轴承的冲击可能只在某个时刻出现，CWT 能保留冲击发生时间及其频带结构。STFT 也可得到时频图，使用固定窗长。小波随尺度伸缩，短小波更适合定位高频瞬态，长小波在低频提供更细的频率刻画。

预加重→128 尺度 Morlet→FFT 卷积取系数→log1p→缩放、归一化、CLAHE

源码用 y[n] = x[n] − 0.97·x[n−1] 预加重，首点沿用原值。尺度数 128、中心参数 1.0、带宽参数 1.5，按 sᵢ = 2·f꜀·128/(128−i) 生成尺度。每轴先计算 128×5000 系数，再经过 log1p、双线性缩放到 224×224、逐图 min-max 转为 8 位灰度、CLAHE。

S项目调用 FFTW，为什么仍然叫 CWT？

答。FFTW 是实现卷积的工具。源码离散化积分 Morlet，按尺度生成反序核，零填充后做 FFT，复数逐点相乘，再做 IFFT。通过差分、除以 FFT 长度、乘尺度因子和居中裁剪得到系数，最后取 abs(Re(coef))。生成的依然是随时间与尺度变化的图。

追问。“是复数模值吗？”当前实现取实部绝对值。abs(Re(z)) 与 sqrt(Re²+Im²) 会得到不同的图，换算法前需做 Python/C++ 对齐并验证模型效果。

A卷积为何补到至少 N+K−1？一轴系数图占多少内存？

答。长度 N 与 K 的线性卷积长度为 N+K−1，频域相乘天然对应循环卷积。零填充到足够长度，避免结果首尾折叠。代码用 next_fast_len 选不小于该长度的 FFT 尺寸。同一轴、同一 FFT 长度可复用输入频谱。一轴系数矩阵 128×5000×4 B = 2.56 MB，峰值还包含 FFT 缓冲、缓存和图像临时对象。

A预加重、log1p 和 CLAHE 分别改变了什么？

答。预加重相对抑制低频和直流，也可能放大高频噪声。log1p 压缩幅值动态范围，并能在零处求值。CLAHE 在局部提升对比度并限制直方图增强，也可能改变噪声纹理。由于逐窗 min-max 弱化绝对幅值信息，要做严重度评估可另保留带单位的 RMS、峰值等特征，并单独验证。

A如果采样率从 50 kHz 改成 25 kHz，输出还是 224×224，可以直接用吗？

答。相同点数对应的观测时长翻倍，同一尺度的伪频率近似随采样率减半，原模型看到的纹理位置会变。compute_cwt_image() 的尺度计算未读取采样率元数据。需要先对齐有效频带、时间窗口和训练分布。若重采样，先确保抗混叠和目标频带仍可观测，再比对融合图与分类表现。

05CCWF 三轴融合

每轴的 CWT 图在融合前又做一次 CLAHE 与反锐化。CCWF 将三张图按 8×8 像素对应分块，计算每块三轴两两的零均值归一化相关性。每个轴取它与另外两轴的映射相关性均值作为权重，随后对同位置像素加权平均。整图归一化转 8 位后，再做融合后 CLAHE 与反锐化，得到单通道图。

ρᵢⱼ = Σ[(Aᵢ−μᵢ)(Aⱼ−μⱼ)] / √[Σ(Aᵢ−μᵢ)² · Σ(Aⱼ−μⱼ)²]
wᵢ = mean over j≠i of (ρᵢⱼ+1)/2
fused = (wₓ·X + wᵧ·Y + w𝓏·Z) / (wₓ+wᵧ+w𝓏)
S若 XY 相关系数为 1，XZ 和 YZ 都为 0，三轴各占多少？

答。映射后三对分数为 1、0.5、0.5。未归一化权重为 0.75、0.75、0.5，合计 2，归一化后分别为 37.5%、37.5%、25%。常量块的分母接近零时，函数将相关系数置 0，映射值为 0.5。代码没有据此剔除常量轴。

S三轴融合一定比单轴好吗？如果故障主要出现在 Z 轴呢？

答。相关性加权偏向跨轴一致的局部纹理。独立轴上的真实弱故障可能被压低，多轴共同噪声也可能被强化。将同一批留出设备和工况分别跑单轴、三轴均值、CCWF 与三通道输入，比较各类召回率、误报、推理与前处理成本。三通道方案需改输入契约并重新训练或适配。

ANCC 与相关性强就代表有同一个故障吗？

答。NCC 描述去掉局部均值后的线性纹理相似度。它可降低单纯亮度偏置对权重的影响，但无法判断同一纹理来自缺陷、传感器耦合还是环境振动。融合前要求三轴时间对齐且尺度映射一致。验证时可人工注入轴间时移、饱和和断线，观察结果是否稳定。

06输入张量与部署对齐

推理取第一张图。三通道输入会转灰度，必要时 resize 到 224×224。像素转为 FP32 后按 (pixel − 33.405) / 78.795 标准化，源码中间没有先除以 255。随后按行展开为 NCHW [1,1,224,224]。模型输出 [1,4]，C++ 取 argmax 和最大分数，类序为 denormal / deballfault / decagefault / deouterrace。

S为什么同样 224×224，Python 的模型结果和 C++ 还可能不同？

答。形状只保证元素组织相容。预加重精度、Morlet 尺度、padding、中心裁剪、实部取绝对值还是复数模、插值、灰度量化、CLAHE、均值方差和类序都会影响结果。用同一 CSV 文件、类别和起始行做逐级对比。当前回放固定正常类和起始段，其他窗口需单独提取或扩展回放接口。比较三轴输入、CWT 矩阵、融合图、张量和四类分数，定位第一次差异。test_cpp_img_fused.png 和 test_cpp_img_fused_bearing.txt 可辅助定位。

A一个输入张量占多少内存？像素 0 和 255 各变成多少？

答。50,176 个 float，共 200,704 B = 196 KiB。0 映射到约 −0.424，255 映射到约 2.812。这个范围有助于排查重复除以 255 等错误。实际峰值内存还包括 OpenCV 中间图、ORT 内部张量和模型权重。

A如果换成真正以 INT8 或 UINT8 为外部输入的模型，现有分支可靠吗？

答。当前轴承模型实际走 float 分支。现有整数输入分支有两处要核对：像素还原与偏移是否等价于新模型的 scale/zero point，以及缓冲区生命周期。两个整数 std::vector 在各自条件分支结束时销毁，CreateTensor 包装的是调用方缓冲，后面的 Run 会引用失效数据。应让缓冲活到 Run 返回，并为每个模型校验类型、shape、元素数与量化参数。

07量化模型与 XNNPACK

模型图可核对。轴承 ONNX 外部输入、输出均为 FP32。图中有 QuantizeLinear / DequantizeLinear 和 INT8 权重张量，尾部是 Softmax 后接 Q/DQ。输入量化节点的 scale 约为 0.0126858，zero point 为 33，末端输出 Q/DQ 的 scale 为 1/256、zero point 为 0。这些是图内量化参数。
量化    q = clamp(round(x/s) + z)
反量化  x̂ = s × (q − z)
S为什么说模型量化了，C++ 却仍然输入 float？

答。外部 I/O 类型和图内表示是两层契约。C++ 把标准化后的浮点数据交给会话，图内通过 Q/DQ 表达量化边界。支持量化融合的执行后端可以为对应子图选择整数内核。仅凭图里有 Q/DQ，无法知道每个节点实际上由哪个 EP 和内核执行。

变式。PTQ 用已有权重与代表性数据确定量化参数，QAT 在训练中模拟量化误差。模型元数据支持曾经经过 ORT 的量化相关流程，仓库未提供校准样本选择、训练方法或精度前后对照。

S为什么日志常见 0.996094？它代表准确率 99.61% 吗？

答。由随附模型末端 Q/DQ 可推得，8 位无符号码最大 255，按 scale=1/256, z=0 得 255/256 = 0.99609375。这与日志值吻合，是单窗口得分可能达到的量化上限。准确率需要独立样本及真实标签，分数校准也需另测。四个分量分别量化后，和也可能偏离 1。

S启用 XNNPACK 就说明用了 NPU、一定更快吗？

答。XNNPACK 是 CPU 执行提供器。代码尝试启用它，XNNPACK 线程数设为 4，ORT intra-op 设为 1 且关闭 spinning。注册抛出异常时把 ORT intra-op 设为 4 并继续创建会话。启用后算子仍可能落到默认 CPU EP。可用 ORT profiling 查看节点分配，并在板上用同一组输入比较 CPU EP 与 XNNPACK 的 P50/P95、吞吐和 CPU 占用。

AHow can a quantized model still take floating-point inputs?

The model exposes a float32 interface. Quantize and dequantize operators define internal quantization boundaries. The execution provider determines which subgraphs can run with quantized kernels. I would confirm the actual placement with ONNX Runtime profiling.

08队列、并发与退出

采集线程 → raw_queue_ → 处理线程（CWT + 推理 + 告警）→ result_queue_ → 日志线程
                               ↓ MenuSnapshot
                             OLED 菜单线程

项目对象启动三个业务线程，菜单还有自己的循环。ConcurrentQueue 用 mutex 保护 FIFO。pop() 以 !empty || stop_ 为条件等待，等待时释放锁，唤醒后重新加锁复查。push() 通知一个消费者，stop() 唤醒所有等待者。菜单通过加锁复制快照，随后在锁外渲染。

S为什么条件变量要写谓词？running_ 用 volatile 可以吗？

答。谓词用于应对虚假唤醒和另一个消费者先取走数据。锁让队列的检查、取出和删除成为一个受保护的步骤。running_ 是独立跨线程状态，可用 atomic 读写。volatile 不提供数据竞争保护，也不负责唤醒阻塞在条件变量上的线程。

S处理变慢，队列会怎样？把队列加大够吗？

答。队列无容量上限，生产长期快于消费时积压，延迟和内存一同增长。按回放约 2 块/秒、假设处理 1 块/秒，每分钟净增约 60 块，仅原始载荷就约 3.6 MB。更大队列只缓冲短峰值。可按业务选有界队列与溢出策略：偏最新告警可淘汰最旧块并记录丢帧，需要连续证据时则要提升吞吐或单独保留原始流。

S调用 stop() 就能排空日志，之后还能直接 start() 吗？

答。项目先把 running_ 设为 false，再停止两个队列并依次 join。队列自身允许取出剩余元素，但业务循环也看 running_，无法保证排空。队列停标志没有复位，空队列上的消费者可能在再次启动后直接退出，且 push() 本身仍允许写入。需要明确关闭是丢弃还是排空，排空时先停生产者，再按依赖顺序关闭并 join 下游，重启前重建或复位队列。硬件读阻塞还需要自己的超时。

AWhat happens if preprocessing is slower than acquisition?

The current FIFO has no size limit, so sustained overload increases memory usage and makes results stale. I would measure queue age and depth, then choose a bounded buffer and a documented overload policy based on whether freshness or uninterrupted evidence matters more.

09置信度、延迟与告警语义

告警候选满足 class_id != 0 && conf >= threshold。菜单初值为 0.50 和 0 秒。延迟打开时，第一次异常记 steady_clock 时间，再次处理到符合条件的结果时才判断是否已到延迟。成功推理的正常类或低分会清除计时。未达到告警条件时，现场输出按类别 0 处理，菜单结果标签与一般日志仍保留模型原始分类。

S报警延迟为什么用 steady_clock？与日志时钟有何区别？

答。延迟计算要用单调时钟，避免改系统时间造成时长跳变。墙钟用于给日志标出日期与时刻。系统仅在有新推理结果时检查是否跨过延迟，因此实际触发可能比设定时间更晚，还受窗口到达节奏影响。

S一次故障后十秒没新数据，再来一帧故障，能算持续十秒吗？

答。代码可能用单调时钟计算首个异常至今的经过时长判定已达门限。采集断流、预处理失败或推理失败路径没有在此处重置计时，故障类别改变也不会单独重置。这个实现无法保证观察到连续同类故障。若业务有此要求，维护显式 正常／候选／告警／数据失效 状态，按类别、序号与最大允许帧间隙更新，并验证失败恢复、跨类切换与断流。

A把阈值提高，就一定能改善现场报警吗？

答。通常会降低触发敏感度，也可能错过低分真故障。把误报、漏报、延迟和错误类别分别统计，再选阈值与延时。分数在阈值边缘来回跳时，可评估进入/退出使用不同阈值或 M-of-N 投票。界面最好同时显示“模型分类”和“告警判定”，避免把抑制中的异常当成正常测量。

10电流环、RS485、OLED 与日志

现场输出包含继电器、74HC595 驱动的指示信号、PWM 对应的电流指令和 RS485 串口帧。PWM 在 GPIO18，频率 1 kHz，由拟合系数把目标电流映射为占空比。待机与推理失败目标电流分别为 4 mA 和 5 mA。四类目标上限为 11、14、17、20 mA，运行中按 8 + (上限−8) × conf 计算目标电流。

A保持架故障置信度 0.8，已通过告警判定，输出多少？

答。保持架为类别 2，上限 17 mA。8 + (17−8) × 0.8 = 15.2 mA，这是软件目标电流，实际值要上板测量。不同类别的电流区间会重叠，例如 10 mA 可由多个类别和分数组合得到。需要无歧义读类时，可用 RS485 帧中独立的类别字段。

ARS485 是 Modbus 吗？tcdrain() 有什么用？

答。RS485 描述物理层。这里走 /dev/ttyAMA0、9600 波特率的自定义 8 字节帧：55 AA | type | class | conf_H conf_L | mA整数 mA小数。先切 DE 发，等待发送队列排空再切回接收，避免最后字节尚在发送时收回驱动。当前帧无 CRC，写入短帧只返回失败，业务端也未完整传播外设失败。

A日志都在日志线程写吗？OLED 是从哪里刷新的？

答。普通推理记录经结果队列写系统日志，告警 CSV 由处理线程同步调用写入。实际 OLED 菜单读快照后刷新，日志线程的 display_results() 只输出到控制台。初始化调用旧日志清理，菜单可导出近期记录到 /tmp/log_export。需评估同步 CSV 写盘对处理时延的影响，以及界面显示的电流与实际下发值是否一致。

A收到掉电预警就能保证日志落盘、告警不会再次拉起吗？

答。代码用原子操作防止回调重复执行，尝试切回待机电流、复位继电器、通知项目停线程，再请求系统关机。回调没有等待业务线程收尾，处理中一块可能仍在写外设或日志。可把输出所有权交给统一状态机，停止接收新任务并规定排空/丢弃策略，按持电时间预算测试掉电、恢复和日志完整性。

11CSV 回放、分段排障与部署

--simulate 接收 CSV 文件。解析器去掉 UTF-8 BOM，识别制表符或逗号分隔，按表头取 de_normal_X/Y/Z，最多读 5000 个有效行，随后按 5000 行一个块循环回放。打开数据源失败时，代码会关闭模拟标志并尝试真实硬件初始化。主程序的 GPIO 初始化和扩展外设路径仍可能执行。

S回放一直预测正常，说明四个类别都验证了吗？

答。默认回放固定取正常列，常见情况是同一块反复输入。它能做冒烟测试和可重复比对。验证四类时应通过单独工具提取窗口，或扩展回放接口以选择类别和起始行，并保留真值，按原始采集序列分组，并覆盖不同运行条件。还可加短文件、坏单元格和丢通道测试。当前逐字段调用 stof，坏值可能抛异常，短文件会回绕拼接，可能制造不连续边界。

S板子在运行，OLED 没更新，怎么快速定位？
  1. 看启动信息和每 5 秒心跳。采集进入而 got_data 不增，先查 ODR、SPI 回读、CSV 加载和采集超时。
  2. got_raw 增长但 cwt_done 不增，查块长度、图像是否空或全零、FFTW 时间和调试写盘。原始队列持续增长时，算消费速率和最老块年龄。
  3. infer_start 与 infer_done 出现长时间缺口，查 Session::Run。两者同增但 output 不增，核对错误码、模型路径和张量。计数说明走到了调用点，无法单独证明外设操作成功。
  4. snapshot 增长后查菜单线程与 OLED/I²C，再查继电器、PWM、串口实际输出和日志权限。先用回放确定软件链路，再接硬件逐段测。
A命令行能运行，systemd 启动却报模型不存在，查什么？

答。先看 ExecStart、WorkingDirectory 和运行用户。模型路径是 ../models/bearing_vibration/bearing_vibration_model.onnx，相对进程工作目录解析。把可执行文件路径写成绝对路径也不会改变这一点。对照安装后的模型位置与运行目录，再查日志目录权限、共享库、串口和 GPIO 访问权限。配置入参 config_path 在业务初始化中被忽略，改 CLI 配置路径无法修复此问题。

S从同一段波形切出很多重叠窗口，随机划分后准确率很高，可信么？

答。相邻窗口共享样本，即使不重叠，也可能共享转速、负载和设备纹理。随机按窗口划分容易产生泄漏。先按采集运行、设备或工况分组，再切窗。归一化统计量和量化校准只从训练侧取，阈值在验证集选，最终测试集只用于报告结果。至少展示每类召回率及其样本量。

S要降低 P95 延迟，你先优化模型还是 CWT？

答。先测端到端并分段打点：首样本/批次结束、入队/出队、CWT 完成、融合完成、ORT Run 完成、外设实际动作。当前 inference_time_us 包含 AI 框架内部图像处理、ORT 和后处理，排除了前面的 CWT 与排队。按 P50/P95、最大积压、长时间 CPU/RSS 判断瓶颈。CWT 慢时优先验证 FFTW plan、核频谱和工作区复用，以及关闭每窗写 PNG 的收益。若 ORT 慢，再查 EP 分配与线程竞争。

A怎么做消融，证明提升来自三轴融合或增强？

答。用同一组分组划分与训练预算，对比单轴、三轴平均、CCWF，进一步逐项去掉预加重、局部增强等。每种预处理用匹配的模型训练和验证，避免把输入分布失配误当成算法收益。对已有模型再做推理时扰动作为鲁棒性实验。报告故障类别的召回、误报与前处理成本，特别看低信噪比与跨转速场景。

AHow would you validate this system on an unseen machine?

I would split by machine or recording run before making windows, then report per-class recall and event-level false alarms. On the target device, I would also measure missed samples and latency from acquisition to alarm. These checks separate generalization from deployment errors.
